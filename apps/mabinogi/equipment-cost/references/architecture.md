# 구조

계산은 `scripts/cost.py`의 `build_row` 한 곳에 모여 있다. 순수 함수라 API·저장소·렌더링과 섞이지 않는다.

```
api.py → normalize.py → store.py → report.py → serve.py
                            ↑           ↑          ↑
                        cost.py    trend.py   inventory.py
                        (원가)     (추세)      (쿠키)
```

`store.py`에는 재고가 없다. 방문자가 가진 재료는 `inventory.py`가 쿠키로 읽고 쓰며, `serve.py`가 요청마다 `build_report(owned=...)`로 넘긴다.

테스트는 `python3 -m pytest tests/ -q` (315개). 픽스처는 2026-08-14T16:17Z 실측 스냅샷이라 시세가 움직여도 흔들리지 않는다. `test_serve.py`만 실제 서버를 띄운다 — 쿠키가 방문자 사이에 안 새는지는 렌더링만 봐서는 확인할 수 없다.

## 재고가 쿠키에 사는 이유

**재고는 브라우저 쿠키(`mabi_inv`)에 산다.** 서버 DB에 두면 여러 사람이 한 서버를 쓸 때 전원이 한 재고를 공유한다 — A가 저장하면 B 화면의 숫자가 바뀐다.

쿠키인 이유는 이 페이지가 서버 렌더링이라서다: 쿠키는 요청에 자동으로 실려 정렬 링크·열 토글 어디서든 그 사람의 재고가 따라오고, 계산은 서버 한 곳에 남는다. 기기를 바꾸면 다시 입력한다(계정은 만들지 않는다).

예전 버전이 DB에 저장해 둔 재고가 있으면 **첫 방문 때 그 브라우저로 한 번 넘어가고 테이블은 사라진다.** 로컬 모드에서만 일어난다 — 공개판에서 하면 첫 방문자가 남의 재고를 가져간다.

## 일봉 수집 주기

일봉은 원본이 두 달치를 주므로 우리가 쌓지 않는다. 서버가 하루 한 번 받는다(`collect.py candles`).

"하루 한 번"은 **마지막으로 받은 시각**으로 잰다(`candle_log` 테이블). 주기 번호(`tick % 480`)로 재면 재시작마다 0으로 돌아가 켤 때마다 다시 받는다 — 실측에서 하루 1번이 의도인데 재시작이 잦은 날 7번 긁었다.

실패해도 받은 것으로 치고 하루 쉰다. 성공했을 때만 적으면 차단이 이어질 때 3분마다 18종을 다시 긁는다. 원본이 매번 두 달치를 통째로 주므로 하루 걸러도 잃는 게 없다 — 다음에 성공할 때 놓친 날까지 들어온다.

## 이 구조가 서 있는 전제

깨지면 구조를 다시 봐야 하는 것들이다.

| 전제 | 깨지면 |
|---|---|
| 시세 이력은 **화면에 쓰는 94종만** 쌓는다 | 잠룡·대연 등 새 등급으로 넓히면 그 종목의 과거가 없다. 넓히는 날부터 다시 쌓인다 |
| 일봉은 **원본이 준다**(3개월치) | 원본이 그 엔드포인트를 없애면 차트가 멈춘다. 우리 `price_history`가 대체하려면 하루 단위 집계를 새로 짜야 한다 |
| 재료는 18종, 완제품은 76종으로 고정 | 게임 패치로 레시피가 바뀌면 `collect.py recipes`를 다시 돌려야 하고, 새 재료의 시세 이력은 그때부터 시작된다 |
| 상세 API는 **레시피 수집에만** 쓴다 | 다른 용도로 부르기 시작하면 IP 쿼터가 배포판을 막는다. 지금 배포판은 이 엔드포인트를 한 번도 부르지 않는다 |
| 재고는 서버에 없다 | 계정·서버 저장을 붙이면 여러 사람이 한 재고를 공유하던 문제로 되돌아간다 |
