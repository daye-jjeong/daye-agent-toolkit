# 실행

## 1. 사실은 직접 찾는다

주제와 관련된 기존 코드·스키마·설정을 먼저 읽는다. 위에 있는 스펙·ADR·구조 문서 중 관련된 것도 읽는다.

**환경에서 확인되는 것을 사용자에게 묻지 마라.** 파일 경로, 현재 동작, 기존 컨벤션, 스키마, 설정값 — 직접 확인한다.

**고칠 대상이 지금 실제로 동작하는지 확인한다.** 코드가 있는 것과 도는 것은 다르다. 테이블이 비었는지, 파일이 0바이트인지, 서비스가 등록돼 있는지, 마지막 기록이 언제인지 — 데이터를 직접 열거나 한 번 돌려본다. 코드만 읽고 넘어가면 **동작하지 않는 것을 고치는 스펙**이 나온다.

**옛 스펙을 읽을 땐 상단 상태 줄부터 본다.** `> 상태: 대체됨`이면 그 문서의 계약 서술은 현행이 아니다 — 결정의 근거(무엇을 재봤고 왜 그렇게 골랐나)만 가져오고, 계약은 대체 문서에서 확인한다. 상태 줄이 없는 옛 문서는 신뢰하지 말고 코드로 대조한다.

찾은 사실을 3~5줄로 요약해 보여준다. 여기서 이미 답이 갈리는 지점이 보이면 그게 첫 질문이다.

## 2. 인터뷰

`mattpocock-skills:grilling`과 `mattpocock-skills:domain-modeling`을 함께 호출한다(`Skill` 도구). 앞이 질문 방식을, 뒤가 ADR·용어집 관리를 맡는다.

> `grill-with-docs`를 부르지 마라. 저 둘을 부르라는 두 줄짜리 래퍼인데 `disable-model-invocation: true`라 `Skill` 도구 호출까지 막힌다. 래퍼를 건너뛰고 알맹이 둘을 직접 부른다.

호출이 실패하면(플러그인 미설치 등) 아래 네 질문만으로 직접 인터뷰한다. 스킬이 없다고 인터뷰를 건너뛰고 다음 단계로 가지는 마라.

인터뷰가 어떻게 흘러가든 **아래 넷은 반드시 답을 받아야 한다.** 스킬이 안 물었으면 직접 묻는다.

| # | 질문 | 안 받으면 |
|---|---|---|
| 1 | 이번에 **안 할 것**은 무엇인가 | 범위가 구현 중에 번진다 |
| 2 | **예외·범위 밖 입력**을 만나면 — 처리하나, 막나, 사람을 부르나 | 구현자가 임의로 메운다 |
| 3 | 실패하면 어떻게 알아채나 | 조용히 깨진 채로 나간다 |
| 4 | 되돌려야 하면 어떻게 | 되돌릴 수 없는 걸 배포한다 |

**2번이 이 커맨드의 존재 이유다.** "그건 그때 알아서"라는 답이 나오면 받아 적지 말고, 구체적인 입력 예를 들어 다시 물어라. 실제 사고는 전부 여기서 났다.

## 3. 테스트 이음새를 맞춘다

스펙을 쓰기 전에 **어디서 테스트할지** 정하고 사용자에게 확인받는다.

- 기존 이음새를 우선한다. 새로 뚫는 것보다 낫다
- 가능한 한 높은 곳에서 잡는다. 이음새는 적을수록 좋고 하나면 가장 좋다
- 새 이음새가 필요하면 어디에 낼지 제안하고 동의를 받는다

여기를 건너뛰면 구현자가 테스트하기 편한 자리에 이음새를 임의로 뚫는다. 2번과 같은 유형의 문제다.

## 4. 스펙을 쓴다

`docs/specs/YYYY-MM-DD-<슬러그>.md`. 없는 디렉토리는 만든다.

```markdown
# <제목>

> 상태: 유효

## 문제
사용자 관점에서 무엇이 불편한가.

## 해결
사용자 관점에서 무엇이 달라지는가.

## 확정된 결정
| 결정 | 선택 | 왜 |
|---|---|---|

## 범위 밖 (이번에 안 하는 것)
- 항목 — 왜 뺐는지 / 언제 할 건지

## 범위 밖 입력을 만나면
2단계 2번의 답. 처리 / 차단 / 에스컬레이션 중 무엇이고 근거는 무엇인지.

## 테스트
3단계에서 맞춘 이음새. 무엇이 되면 done인지.

## 미해결
답이 안 난 것. 없으면 "없음".

---
구현 중 이 문서와 달라지면 **문서를 먼저 고치고 간다.**
뒤집기만이 아니라 늘어난 것·줄어든 것·자리를 옮긴 것도 포함한다.
끝나면 각 섹션을 산출물과 한 번 대조한다.
```

맨 아래 줄은 지우지 마라. **구현은 다른 세션에서 일어나고 그때 이 커맨드는 로드되지 않는다.** 스펙 파일만 따라가므로, 구현자를 향한 지시는 파일 안에 있어야 닿는다. 위 4단계 규칙(스펙끼리 잇기)은 스펙을 *쓰는* 사람을 향하고 이 줄은 *읽고 구현하는* 사람을 향한다 — 자리가 다르다.

**파일 경로와 코드 스니펫을 넣지 마라.** 금방 낡아 스펙 전체의 신뢰를 깎는다. 예외는 결정 자체를 산문보다 정확히 담는 경우뿐이다(상태 기계, 스키마, 타입 모양).

**"범위 밖"과 "범위 밖 입력을 만나면"을 비워두지 마라.** 비었다는 건 인터뷰가 덜 끝났다는 뜻이다.

### 기존 스펙을 뒤집었으면 양쪽을 잇는다

스펙은 **그때의 결정 기록**이다. 뒤집혔다고 본문을 고쳐 쓰지 마라 — 무엇이 왜 틀렸는지가 다음 결정의 재료다. 대신 상태 줄로 잇는다.

옛 스펙의 결정을 하나라도 뒤집으면 **같은 커밋에** 둘 다 한다. 나눠 놓으면 뒤쪽을 안 한다.

```markdown
# 옛 스펙 상단
> 상태: 대체됨 → docs/specs/2026-08-08-<슬러그>.md
> <한 줄: 무엇이 뒤집혔나>

# 새 스펙 상단
> 상태: 유효
> 대체: docs/specs/2026-08-06-<슬러그>.md 의 <어느 결정>
```

전체가 아니라 일부만 뒤집혔으면 옛 스펙은 `유효`로 두고 뒤집힌 결정 행에만 표시한다. 문서는 컴파일이 안 돼서 **"뒤집혔는데 아무도 모름"이 기본값**이다. 이 줄이 유일한 방어다.

grep으로 훑을 수 있게 `> 상태:` 형태를 그대로 쓴다.

## 5. 구조를 건드렸으면 문서를 갱신한다

ADR과 용어집(`CONTEXT.md`)은 `grill-with-docs` 안의 `domain-modeling`이 맡는다. 그 기준을 따르되, **그 스킬이 다루지 않는 것 하나를 직접 챙긴다.**

`ARCHITECTURE.md` — 지금 구조가 어떻게 생겼고 무슨 전제 위에 서 있는지. 없으면 만든다.

```markdown
# 구조

## 구성
무엇이 어디 있고 어떻게 연결되는지. 현재 상태만. 역사는 ADR이 갖는다.

## 전제
이게 참이라서 이 구조가 성립한다. 깨지면 구조를 다시 봐야 하는 것들.
- 전제 — 깨지면 무슨 일이 나는지
```

**전제 섹션이 핵심이다.** 구현자가 범위 밖 입력을 임의로 처리하는 건 그게 전제였는지 몰라서다. 이번 작업으로 전제가 생기거나 깨졌으면 반드시 적는다.

ADR은 결정 시점의 기록이라 쌓이고 `ARCHITECTURE.md`는 현재 스냅샷이라 갱신된다. 구조를 바꾸면서 둘을 같이 안 건드리면 이 파일은 곧 거짓말이 된다.

## 6. 여기서 멈춘다

스펙 경로를 알리고 사용자 검토를 받는다. **승인 전에 구현하지 마라.**

승인 후에도 이 세션에서 이어서 구현하지 마라 — 인터뷰 기록이 컨텍스트를 채운 상태라 구현 중 초기 합의가 밀려난다. 새 세션에서 스펙 파일을 읽고 시작하라고 안내한다.
