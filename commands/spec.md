# 실행

## 1. 사실은 직접 찾는다

주제와 관련된 기존 코드·스키마·설정을 먼저 읽는다. 위 목록에 관련 스펙·ADR이 있으면 그것도 읽는다.

**환경에서 확인되는 것을 사용자에게 묻지 마라.** 파일 경로, 현재 동작, 기존 컨벤션, 스키마, 설정값 — 직접 확인한다.

찾은 사실을 3~5줄로 요약해 보여주고 인터뷰를 시작한다. 여기서 이미 답이 갈리는 지점이 보이면 그걸 첫 질문으로 삼는다.

## 2. 인터뷰 — 사실은 내가, 결정은 사용자가

결정 트리를 하나씩 내려간다.

- **한 번에 하나.** 여러 개를 같이 던지면 답이 뭉개진다
- **매 질문에 추천 답을 붙인다.** "A와 B 중 뭐가 좋을까요?"가 아니라 "A를 추천한다 — 이유는 X. B로 가면 Y를 감수해야 한다"
- 앞 답이 뒤 질문을 바꾸면 순서를 다시 잡는다
- 결정 트리가 닫힐 때까지, 또는 사용자가 그만하라고 할 때까지

**반드시 답을 받아야 하는 넷:**

| # | 질문 | 안 받으면 |
|---|---|---|
| 1 | 이번에 **안 할 것**은 무엇인가 | 범위가 구현 중에 번진다 |
| 2 | **예외·범위 밖 입력**을 만나면 — 처리하나, 막나, 사람을 부르나 | 구현자가 임의로 메운다 |
| 3 | 실패하면 어떻게 알아채나 | 조용히 깨진 채로 나간다 |
| 4 | 되돌려야 하면 어떻게 | 되돌릴 수 없는 걸 배포한다 |

**2번이 이 커맨드의 존재 이유다.** 여기서 "그건 그때 알아서"라는 답이 나오면 그대로 받아 적지 말고, 구체적인 입력 예를 들어 다시 물어라. 실제 사고는 전부 여기서 났다.

## 3. 스펙을 쓴다

`docs/specs/YYYY-MM-DD-<슬러그>.md`에 저장한다. 없는 디렉토리는 만든다.

```markdown
# <제목>

## 만들 것
한두 문단. 무엇이 어떻게 달라지는지 사용자 관점에서.

## 확정된 결정
| 결정 | 선택 | 왜 |
|---|---|---|

## 범위 밖 (이번에 안 하는 것)
- 항목 — 왜 뺐는지 / 언제 할 건지

## 범위 밖 입력을 만나면
인터뷰 2번의 답. 처리 / 차단 / 에스컬레이션 중 무엇이고, 그 근거.

## 검증
무엇이 되면 done인지. 테스트로 확인 가능한 형태로.

## 미해결
답이 안 난 것. 없으면 "없음".
```

**"범위 밖"과 "범위 밖 입력을 만나면"은 비워두지 마라.** 비었다는 건 인터뷰가 덜 끝났다는 뜻이다.

## 4. 구조를 건드렸으면 ADR

경계·계약·데이터 소유권이 바뀌는 결정만. 컨벤션이나 구현 선택은 해당 없다.

`docs/adr/NNNN-<슬러그>.md` (번호는 기존 최대값 + 1):

```markdown
# NNNN. <결정>

- 상태: 채택
- 날짜: YYYY-MM-DD

## 맥락
무엇이 문제였나. 실제 사례가 있으면 인용.

## 결정
무엇으로 정했나.

## 결과
얻는 것과 포기하는 것. 이 결정 때문에 앞으로 못 하게 되는 일.
```

새 용어가 생겼으면 `CONTEXT.md`에 한 줄 추가한다(없으면 만든다). 팀이 이미 쓰는 말로 적고, 지어낸 이름을 넣지 마라.

## 5. 여기서 멈춘다

스펙 경로를 알리고 사용자 검토를 받는다. **승인 전에 구현하지 마라.**

승인 후에도 이 세션에서 이어서 구현하지 마라 — 인터뷰 기록이 컨텍스트를 채운 상태라 구현 중 초기 합의가 밀려난다. 새 세션에서 스펙 파일을 읽고 시작하라고 안내한다.
