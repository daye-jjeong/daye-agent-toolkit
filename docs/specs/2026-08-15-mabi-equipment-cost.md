# 마비노기 모바일 잔영·해연 장비 원가 비교

> 상태: 유효

## 문제

잔영·해연 장비를 거래소에서 사는 게 싼지 만드는 게 싼지 매번 손으로 따져야 한다. 무기 하나에 재료가 6종 들어가고 각 재료 시세가 따로 움직인다. 한 아이템을 판단하려고 거래소를 예닐곱 번 조회해야 하고, 76종 전체를 비교하는 건 사실상 불가능하다.

여기에 "잔영 11개 = 해연 1개"라는 등가 관계가 커뮤니티에서 통용된다. 잔영을 감정할 때 오르는 마도저항을 11개분 쌓으면 해연 1개의 최소 수치와 같다는 뜻이다. 그런데 그게 실제로 돈으로 이득인지 확인할 방법이 없다.

## 해결

페이지를 열면 **해연 38종**이 부위별로 묶여 나온다. 행마다 해연 하나를 손에 넣는 네 길이 나란히 선다 — 해연 구매, 해연 제작, 같은 종류 잔영×N 구매, 잔영×N 제작. 그중 가장 싼 칸에 표시가 붙고, 해연을 그냥 살 때보다 얼마나 아끼는지 옆에 나온다. 레시피 제작은 별도 열이고 조건부라 후보에서 뺀다.

행을 누르면 아래에 상세가 열려 경로별 재료의 수량·단가·소계·매물 수가 나온다. 원가에서 어느 재료가 지배적인지 바로 보인다. 실측 예로 해연의 커브드 하프ZZ는 망령의 영혼석 한 종이 재료비의 54%를 차지한다.

가진 재료를 맨 위에 적어 두면 제작 칸에 실지출이 함께 나온다. 그 재고는 **방문자의 브라우저 쿠키**에 남는다 — 서버는 누가 뭘 가졌는지 모른다.

시세 기준 시각은 페이지 위쪽에 항상 떠 있다. 로컬에서는 새로고침 버튼으로 받고, 공개 배포판(`--public`)에서는 서버가 3분마다 직접 받는다.

## 확정된 결정

| 결정 | 선택 | 왜 |
|---|---|---|
| 데이터 출처 | mabimobi.life 비공식 API 3종 — `GET /d/api/v1/market/prices?limit=500&offset=N`(시세), `GET /d/api/v1/items?search=<말머리>&limit=200`(목록), `GET /d/api/v1/items/<id>`(상세) | 넥슨 오픈 API는 마비노기 모바일을 지원하지 않는다. 이 API 하나에 시세와 제작 레시피가 모두 있다 |
| 재료↔시세 매칭 키 | 재료의 `itemId` = 시세의 `codex_item_id` | 상세 응답의 재료 객체에는 `market_kind_id`가 없다(아이템 자체 필드는 null이다). 이름 매칭은 쓰지 않는다 — 시세 1,226건에 동명 항목이 74건 있다. `codex_item_id`는 76종 전부에서 중복이 없다(실측) |
| HTTP 클라이언트 | python 표준 라이브러리 urllib | 같은 요청을 curl로 보내면 403, urllib로 보내면 200이다(실측). TLS 지문 차이로 보인다. **curl이나 외부 HTTP 라이브러리로 바꾸면 차단된다** |
| 게임 클라이언트 패킷 | 쓰지 않는다 | 약관 위반이고 계정 정지 사유다. 게다가 필요한 데이터가 이미 API에 정형화돼 있어 얻을 게 없다 |
| 레시피 저장 | 1회 수집 후 DB에 고정 | 아이템 상세 API에만 IP 단위 쿼터가 걸린다. 레시피는 게임 패치 전까지 바뀌지 않으므로 반복 조회할 이유가 없다 |
| 시세 갱신 | 주기 자동 수집, **기본 3분** | 시세 API는 쿼터가 없다(1,226건 1.7초). 처음엔 10분으로 잡았고 근거는 "원본 변동 지표 최소 단위가 1시간"이었는데, 실제 저장된 기준 시각은 1·5·17·23·31·37분 간격으로 움직였다 — 원본은 그보다 훨씬 자주 갱신된다. 10분 주기는 그 사이 변동을 흘린다. 같은 기준 시각은 중복 저장하지 않으므로 촘촘히 받아도 이력이 부풀지 않는다. 주기는 설정값 |
| 공개판 신선도 임계 | 15분 (주기의 5배) | 3분마다 받는데 임계가 30분이면 열 번 연속 실패해야 경고가 뜬다. 수집이 멈춘 걸 화면으로 알아채는 게 임계의 목적이라 주기를 따라 내려와야 한다. 로컬은 손으로 새로고침하므로 기존 30분을 유지한다 |
| 저장소 | SQLite | 시세를 갱신할 때마다 이력이 남는다. 외부 의존성 없이 표준 라이브러리로 처리된다 |
| 잔영 11개 비교 | 가격 등가만 계산, 11은 설정값 | 부위별 마도저항 수치표를 구하지 못했다. 가격 비교는 지금 데이터로 정확하고, 배수를 페이지에서 바꿀 수 있게 하면 수치가 틀려도 페이지가 거짓을 말하지 않는다 |
| 레시피 제작 경로 | "레시피 보유 시" 조건부 행으로 분리 | 레시피 아이템은 거래 불가라 시세가 없다. 원가 0으로 합산하면 레시피 제작이 압도적으로 싸 보이는 착시가 생긴다. 같은 줄에 세워 직접 비교하지 않는다 |
| 레시피가 있는 등급 | 해연만. 잔영 행의 레시피 칸은 비운다 | 레시피 아이템이 해연 38종에만 존재하고 잔영은 0건이다(실측). 상세 응답의 `crafting.made_by`는 배열이고, 있으면 `[0]`이 일반 제작·`[1]`이 레시피 제작이다. 레시피 경로는 재료 수량이 대략 절반이다(망령의 영혼석 80→40) |
| 원가 기준 | 최저가 × 수량 = 하한선 | API에 호가 분포가 없고 최저가는 1개 기준이다. 80개를 실제로 사면 최저가부터 위로 훑어 올라가므로 실제 지출은 이보다 크다. 페이지에 하한선임을 명시한다 |
| 실패 감지 | 페이지에 시세 기준 시각 상시 표시, 임계 초과 시 경고 | 수집기가 죽어도 페이지는 멀쩡한 숫자를 계속 보여준다. 보는 순간 신선도가 눈에 들어와야 한다. 임계는 설정값 |
| 신선도 판정 기준 | 원본 스냅샷 시각이 아니라 **우리가 마지막으로 받은 시각**(`collect_log`) | 처음엔 `as_of` 하나로 쟀는데, 실측에서 원본이 07:14부터 07:35까지 21분간 같은 값을 줬다. 그 사이 수집기는 3분마다 일곱 번 정상 수집했는데 화면은 "임계를 넘었다. 수집기가 멈췄는지 확인할 것"을 띄웠다 — 멀쩡한 걸 고장났다고 한 것이다. 경고는 우리가 고칠 수 있는 것에만 붙어야 한다. 원본이 늦는 건 `source_lagging`으로 회색 문장을 하나 더할 뿐 경고하지 않는다 |
| 수집 시각을 어디 남기나 | `collect_log` 한 행 (`price_history`가 아니라) | 같은 스냅샷은 중복 저장을 건너뛰므로, 원본이 새 값을 안 주는 동안엔 아무리 받아도 `price_history`에 흔적이 없다. "받았다"는 사실 자체를 따로 남겨야 두 시계를 가를 수 있다 |
| 시각 표시 | `<time datetime>`로 UTC를 내보내고 브라우저가 로컬 시각으로 바꾼다 | 원본이 주는 값은 UTC다. `07:36`이라고만 쓰면 한국에서 보는 사람은 9시간 어긋난 걸 모른다. 서버가 시간대를 정하면 방문자마다 틀린다. JS가 안 돌면 `07:36 UTC`가 그대로 남아 여전히 정확하다. "N분 전"은 서버가 계산하므로 시간대와 무관하다 |
| 수집 실패 표시 | 실패 이유와 연속 횟수를 상단 띠에 | 콘솔 로그는 방문자가 못 본다. 아무 말 없이 낡은 값을 보여 주면 그게 최신인 줄 안다. 임계를 넘길 때까지 기다리면 15분 늦고, 넘겨도 "낡았다"만 말하지 이유가 없다 |
| 배치 위치 | standalone 스킬 한 벌(스킬 본문 + 수집·서버 스크립트 + 테스트) | 이 레포의 기존 스킬 구조를 그대로 따른다. 표준 라이브러리만 쓰는 제약도 이미 충족된다 |
| 표의 단위 | 행은 **해연 38종**. 잔영은 행이 아니라 등가 경로로 들어온다 | 알고 싶은 건 "해연 한 종을 어떻게 손에 넣는 게 싼가"다. 잔영을 따로 38행 세우면 같은 정보가 두 번 나오고, 잔영 행의 등가 칸은 자기 자신×N이라 뜻이 없었다 |
| 판정 기준 | 해연 구매 · 해연 제작 · 잔영×N 구매 · 잔영×N 제작 4자 중 최저 | 원래는 사기 대 만들기 2자였다. 잔영을 사는 길과 만드는 길은 값이 크게 다르다 — 실측에서 잔영 제작비는 시세의 두 배 안팎이라, 하나로 뭉뚱그리면 어느 쪽을 말하는지 알 수 없다. 레시피 제작은 조건부라 후보에서 뺀다 |
| 보유 재료 값 매김 | **두 값을 나란히 둔다** — 전체 시세(기회비용)와 실지출(보유분 0원) | 재료를 이미 가졌을 때 "지금 지갑에서 얼마 나가나"와 "재료를 그냥 팔지 만들어 팔지"는 다른 질문이고, 답도 다르다. 하나만 두면 나머지 질문에 거짓말을 한다 |
| 보유 기준 판정 | 판정은 **전체 시세** 기준을 유지한다 | 이미 가진 재료도 팔 수 있으므로, 만들지 말지를 정할 땐 기회비용이 옳다. 실지출을 판정에 쓰면 "재료가 있으니 뭐든 만드는 게 이득"이라는 틀린 결론이 나온다. 실지출은 현금 흐름 정보로 옆에 둔다 |
| 상세 펼침 방식 | 값 행 아래에 **별도 행**으로 연다 | 첫 칸 안에서 펼치면 그 셀만 부풀어 옆 칸(구매가·매물)이 세로로 밀린다. 표는 한 줄로 읽혀야 한다 |
| 상세 금액 | 소계와 **실 소계**를 나란히 | 소계만 있으면 "이 재료가 원가를 지배한다"는 것만 알고 "그중 실제로 사야 할 건 얼마"는 모른다. 망령의 영혼석은 소계 7,520인데 76개를 이미 가져 실지출은 376이다 |
| 재료 상세 정렬 | 소계가 큰 순 | 원가를 무엇이 지배하는지가 이 표를 여는 이유다. 이름순으로 세우면 그걸 눈으로 찾아야 한다 |
| 재료 입력칸 묶음 | 영혼석 · 마력석 · 그 밖의 재료, 기본값 0 | 18칸이 한 줄로 늘어서면 어디에 넣을지 헤맨다. 빈 칸보다 0이 낫다 — 안 가졌다는 걸 눈으로 확인할 수 있다 |
| 미저장 입력 보존 | 브라우저 localStorage에 초안 보관 | 저장을 누르기 전에 새로고침하면 입력이 통째로 날아간다. 되살릴 때는 그 사실을 알린다 — 조용히 되살리면 저장된 값과 헷갈린다 |
| 보유 재료 입력 | 페이지 **맨 위**에 재료별 입력칸 | 재료 57종 중 거래 가능한 건 18종뿐이라 칸을 다 세워도 된다. 이름을 타이핑하게 하면 오타가 조용히 삼켜진다 — 폼 필드를 `qty_<id>`로 두면 그 문제가 사라진다. 표 아래 두면 스크롤해야 보여서 안 쓰게 된다 |
| 보유 재료 저장 위치 | **브라우저 쿠키** (`mabi_inv`). 서버 DB에 두지 않는다 | 여러 사람이 한 서버를 쓰면 DB에 둔 재고가 전원 공유가 된다 — A가 저장하면 B 화면의 숫자가 바뀐다. localStorage가 아니라 쿠키인 이유는 이 페이지가 서버 렌더링이고 실지출 계산도 서버가 하기 때문이다. 쿠키는 요청에 자동으로 실려서 정렬 링크·새로고침·열 토글 어디서든 그 사람의 재고가 따라온다. localStorage였다면 매 요청마다 JS로 재고를 보내고 화면을 다시 그려야 하고, 계산이 Python과 JS로 갈라진다. 18종을 다 채워도 220바이트 남짓이라 4KB 한도에 여유가 크다 |
| 쿠키 값 형식 | `9283:80.9421:12` — 항목은 `.`, 키·값은 `:` | 쉼표는 쿠키 구분자라 값에 못 쓴다(RFC 6265 cookie-octet에서 제외). `.`과 `:`는 허용되고 인코딩 없이 그대로 읽힌다. JSON+base64는 같은 정보에 세 배를 쓰고 눈으로 못 읽는다 |
| 공개 배포 모드 | `--public` — 새로고침 버튼을 끄고 서버가 직접 주기 수집 | 버튼은 누를 때마다 원본 API로 요청이 나간다. 여러 사람이 각자 누르면 **서버 IP 하나로** 몰린다. 수집은 서버가 10분마다 한 번만 하고 방문자는 그 결과를 본다. 같은 플래그로 `0.0.0.0`에 바인딩한다 — 이 셋은 "여러 사람이 쓰는 배포판"이라는 한 덩어리라 따로 켜고 끌 이유가 없다 |
| 잔영 짝짓기 | 각 해연은 **같은 종류** 잔영과 짝짓는다 | 감정 재료는 종류를 섞을 수 있어서, 한때 "부위 안에서 가장 싼 잔영"으로 계산했다. 그러나 열 정렬이 생긴 뒤로는 종류 간 비교를 정렬로 할 수 있어 되돌렸다 — 행마다 다른 종류를 가리키면 그 행이 무엇을 말하는지 읽기 어렵다 |
| 화면 새로고침 | 버튼 → 백그라운드 수집 + 실제 건수 진행바 | 수집이 끝날 때까지 응답을 붙들면 화면이 얼어붙는다. 즉시 돌려주고 `/refresh/status`로 진행을 물어본다. 진행바는 실제 받은 건수로 그린다 — 총량을 모르니 직전 건수를 추정치로 쓰고 넘으면 100%에서 멈춘다. 추정할 근거가 없으면 비율을 지어내지 않고 흐르는 막대만 둔다. 서버는 `ThreadingHTTPServer`여야 수집 중에도 상태를 물어볼 수 있다 |
| 열 정렬 | 모든 금액 열을 헤더 클릭으로 오름·내림 정렬 | 76종을 눈으로 훑어 최저를 찾을 수 없다. 값이 없는 행(계산 불가·미수집)은 방향과 무관하게 뒤로 보낸다 |
| 배수 기본값 | 10 | 사용자가 실제로 쓰는 값이다(기존 11은 출처 미확인 커뮤니티 값). 판정이 배수에 크게 흔들린다 — 10이면 38종 중 36종이 "잔영 구매"인데 11이면 26종으로 준다. 그래서 페이지에서 바꿀 수 있어야 한다 |
| 부위 묶음 | 무기 → 투구 → 상의 → 하의 → 장갑 → 신발 → 목걸이 → 반지 | 76종을 한 줄로 세우면 상의끼리 견줄 수가 없다. 묶음 안에서는 아끼는 금액 순 |
| 레시피 열 숨기기 | `?recipe=0` | 레시피가 없으면 그 열은 볼 이유가 없고, 잔영 38종에는 아예 값이 없다 |

## 범위 밖 (이번에 안 하는 것)

- **마도저항 수치 계산** — 부위별 수치표를 구하지 못했다. 840과 420 두 값만 파편적으로 확인됐고 전체 표가 없다. 가격 등가 비교로 대체한다. 수치표가 확보되면 그때 넣는다
- **시세 추이 그래프** — 이력은 쌓되 그리지 않는다. 만든 직후에는 데이터가 없어 빈 화면이 된다. 며칠 쌓인 뒤에 판단한다
- **잠룡·대연·드래케인 등 다른 등급** — 레시피 수집량이 쿼터를 크게 넘어 수집에만 몇 시간이 든다. 잔영·해연 구조가 자리 잡은 뒤에 확장한다
- **대성공 확률 반영** — 일반 제작에만 대성공이 있어 실제 기대값은 일반 제작 쪽이 조금 더 유리하다. 확률값을 확인하지 못해 재료비만 계산한다
- **감정 순서 메커니즘** — 해연을 먼저 감정하면 부위 상한이 풀려 잔영이 최대치까지 붙는다는 동작이 확인됐으나 모델링하지 않는다. 마도저항 계산을 뺐으므로 함께 뺀다
- **거래소 수수료·세금** — 반영하지 않는다. 구매가와 재료비를 같은 기준(표시가)으로 두어 비교의 일관성을 지킨다
- **계정·로그인** — 공개 배포하지만 사용자를 식별하지 않는다. 서버가 개인 데이터를 하나도 안 갖는 게 재고를 쿠키로 옮긴 이유이고, 계정을 붙이면 그게 도로 무너진다. 기기를 바꾸면 재고를 다시 넣는다

## 범위 밖 입력을 만나면

전부 **처리하되 표시한다**. 막지도 않고, 조용히 메우지도 않는다.

| 상황 | 처리 |
|---|---|
| 재료가 거래 불가 | 그 재료를 합계에서 빼고, 뺐다는 사실을 해당 경로에 라벨로 붙인다. 경로 자체는 살린다. 레시피 아이템만이 아니다 — `세공된 페리도트ZZ`처럼 평범해 보이는 재료도 거래 불가다(페리도트 링·네크리스 4종이 여기 걸린다). 거래 가능 여부는 상세 응답의 재료 객체에 없으므로 아이템 목록 API로 따로 채운다 |
| 재료 시세가 아예 없음 | 그 경로 전체를 "계산 불가"로 표시한다. 0이나 추정치로 메우지 않는다 |
| 완제품 매물이 0 | "매물 없음"으로 표시하고 **거래소만 선택지에서 뺀다**. 남은 선택지(제작·잔영 등가)끼리는 그대로 비교한다 — 살 수 없다는 것 자체가 판단에 필요한 정보다. 직전 가격을 현재가로 쓰지 않는다. 선택지가 하나도 안 남으면 그때는 결론을 내지 않는다 |
| 매물 수량이 필요 수량보다 적음 | 계산은 그대로 하되 해당 재료 행에 경고를 남긴다. 하한선과 실제의 격차가 커지는 구간이다 |
| 상세 API가 쿼터를 반환 | 수집을 멈추고 이미 받은 레시피는 유지한다. 부분 수집분을 버리지 않고 다음 주기에 못 받은 것부터 이어받는다 |
| 수집기가 멈춤 | 상단 띠가 **마지막으로 받은 시각**을 말하며 경고로 바뀐다. 낡은 숫자를 최신인 것처럼 보여주지 않는다 |
| 원본이 새 값을 안 줌 | 경고하지 않는다. "원본이 그 뒤로 새 값을 안 준다"를 회색으로 덧붙이고 받은 시각을 함께 보인다 — 새로고침해도 숫자가 안 바뀌는 이유가 거기 있다 |
| 주기 수집이 실패함 | 이유와 연속 실패 횟수를 상단 띠에 띄운다. 서버는 계속 돈다 — 한 번 끊겼다고 페이지 전체가 사라지면 안 된다 |
| 잔영에 대응하는 해연이 없거나 그 반대 | 등가 비교 칸을 비운다. 지금은 38종이 1:1로 모두 대응하지만 패치로 깨질 수 있다 |
| 레시피 제작 경로가 아예 없음(잔영 전체) | 레시피 칸을 비운다. "0원"이나 일반 제작 값 복사가 아니다 |
| 쿠키가 깨졌거나 모르는 재료 id가 들어 있음 | 그 항목만 버리고 나머지는 살린다. 폼 입력과 달리 쿠키는 사용자가 방금 친 값이 아니라 알릴 데가 없다 — 패치로 재료가 바뀌면 여기서 조용히 정리된다 |
| 공개 모드에서 `POST /refresh` | 404로 막는다. 버튼도 안 그린다 — 화면에 없는 걸 직접 부르는 건 우리가 의도한 사용이 아니다 |

## 테스트

이음새는 **원가 계산 순수 함수 한 곳**이다. 레시피와 시세를 딕셔너리로 받아 비교행을 돌려준다. API 호출·저장소·렌더링은 이 함수 바깥에 얇게 둔다.

픽스처는 2026-08-14T16:17Z 스냅샷을 쓴다. 해연의 커브드 하프ZZ — 거래소 23,174 / 일반 제작 재료비 15,165 / 레시피 제작 재료비 8,322.

일반 제작 재료는 특급 목재 5, 백금강괴 5, 허상의 마력석 15, 망령의 영혼석 80, 야생의 영혼석 75, 파동의 영혼석 90이다. 레시피 제작은 여기에 레시피 1개(거래 불가)가 붙고 나머지가 5·5·8·40·38·45로 줄어든다.

재료비 두 값은 최초 조사 때보다 각각 45·19 낮다. 재료 구성과 수량은 그대로이고 시세만 내렸다. 시세는 계속 움직이므로 테스트는 실시간 조회가 아니라 이 고정 스냅샷만 본다.

## 미해결

- **"11"이라는 숫자의 출처를 확인하지 못했다.** 커뮤니티에서 통용되는 값이고 사용자 확인도 받았으나, 원문(dcinside 게시글)은 본문과 댓글이 로드되지 않았다. 설정값으로 두었으므로 페이지가 틀린 주장을 하지는 않지만, 기본값 11의 근거는 미상이다
- 부위별 마도저항 수치표가 없다. 잔영 최대치와 해연 최소치가 같은 구조라는 것, 그 값이 840이고 반지는 420이라는 파편만 확인됐다
- 상세 API의 쿼터는 **한 번에 39종**에서 끊겼다(스펙 작성 시 추정한 60~70종보다 낮다). 76종을 한 번에 받을 수 없으므로 이어받기가 필수다. 이어받기는 실제로 39종 + 37종으로 완결됐다.
- **429 본문의 `Expected available in N seconds`를 믿고 재시도하면 안 된다.** 39종에서 끊긴 뒤 5분 간격으로 8번(약 40분) 재시도했으나 전부 429였고, 그 사이 한 건도 더 받지 못했다. 몇 시간 뒤에는 풀려 있었고 남은 37종이 한 번에 들어왔다. 429 요청 자체가 창을 갱신하는지는 확인하지 못했다. **재시도 간격은 시간 단위로 잡거나, 끊기면 그날은 멈추고 다음 실행에 맡기는 게 안전하다**

**해소됨** — `attributes`에 감정 옵션 수치는 **없다**. 들어 있는 것은 장비 고정 속성(`main_attribute_min`/`max` = 공격력 3594~3983 등)과 제작 레시피(`crafting.made_by`)다. 그러므로 마도저항 계산은 범위 밖으로 남는다. `arcane_resistance`라는 필드가 있기는 하나 정수 1111250886으로 들어온다 — float32 비트로 읽으면 47.09지만 그 해석이 맞는지 확인되지 않았고, 감정으로 붙는 옵션이 아니라 장비 자체 속성으로 보인다. 쓰지 않는다
